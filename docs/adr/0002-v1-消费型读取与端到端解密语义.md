# ADR-0002：API v1 消费型读取与端到端解密语义

- 状态：已接受
- 日期：2026-08-24
- 适用范围：`/api/v1` 文本读取、原始文本、文件预览与文件下载

## 背景

API v1 在服务器授权并返回内容时原子增加访问计数。端到端密钥位于 URL fragment，
不会发送给服务器，因此服务器既不能验证密钥，也不能知道客户端是否成功解密。
另外，服务器完成计数后到客户端完整收到响应之间可能发生断线；此时客户端无法可靠
判断访问是否已经被计入。

把 `max_views` 解释成“成功解密次数”在现有零知识协议下不可实现。仅知道短码的第三方
也可能领取密文并消耗次数；E2E 保护的是机密性和完整性，不保证短码泄露后的可用性。

## 决策

API v1 冻结以下语义：

1. 一次访问是“服务器成功授权的一次内容领取”，不是“客户端成功展示、保存或解密”。
2. `readShare`、`readShareRaw`、`previewFile` 与 `downloadFile` 都是消费型操作；元数据、
   页面 shell 与二维码不是消费型操作。
3. 消费型操作禁止客户端、Service Worker、HTTP 库或后台任务自动重试。超时、取消、
   响应解析失败或流中断均必须显示“结果未知”，不得展示“检查网络后重试”。
4. E2E 客户端必须在请求前校验已有 fragment 的完整语法和 43 字符密钥编码长度；这能
   避免明显非法密钥造成无意义消费。fragment 完全缺失时，只有领取后看到 ENC1 才能
   判断需要密钥；错误但格式合法的 32-byte 密钥同样只能在领取密文后识别。
5. 创建与上传使用 `Idempotency-Key`；网络结果未知时复用完全相同的请求体、密文、
   E2E 密钥和幂等键。消费型 GET 不复用创建幂等机制。
6. UI 必须说明访问次数按服务器领取计数；解密失败不会退回次数。

OpenAPI 继续使用 `x-clipshare-consumes-view` 与 `x-clipshare-auto-retry` 作为机器契约。

## 被否决的替代方案

- “解密失败后回滚次数”：服务器不知道解密结果；接受客户端回执会允许任意领取者谎报
  失败并绕过次数限制。
- “对 GET 使用普通 Idempotency-Key”：长期重放会改变一次性分享的安全边界；短期领取
  claim 的生命周期、绑定对象、并发和重放语义需要独立协议，不能复用创建记录偷渡。
- “客户端收到错误就自动重试”：HTTP 错误可分类，但超时与中途断线无法证明服务端未
  提交计数，会造成额外消费。

## 后果与后续演进

API v1 的机密性保持不变，但不能承诺“成功解密次数”或抗短码泄露的可用性。需要可恢复
领取时，应在新协议版本设计短期高熵领取 claim/票据，明确首次领取、响应恢复、过期、
并发、撤销和日志隐私；该设计必须新增 ADR 和威胁模型，不得静默改变 v1。

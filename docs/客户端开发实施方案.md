# ClipShare Windows/Android 客户端开发实施方案

> 状态：方案已确定；`v0.3-G0` 测试隔离与治理前置模块已于 2026-08-23 验收通过，当前进入 `v0.3-C1`。客户端整体仍为 **NO-GO（尚不可上线）**。
>
> 依据：仓库内 [项目书与开发手册约束快照](依据/项目书与开发手册约束快照.md)、系统设计/API/部署文档，以及 Windows、Android、协议安全、QA/发布四个只读 Agent 的交叉评审。

## 1. 目标与非目标

### 1.1 v0.3 目标

- Windows 原生客户端：托盘、全局快捷键、显式上传/领取、可选剪贴板监听、流式文件传输、E2E、本地加密历史。
- Android 原生客户端：系统 Sharesheet、前台显式粘贴、链接/短码领取、SAF 流式文件传输、E2E、本地加密历史。
- 两端共享同一 OpenAPI/错误语义和同一密码学测试向量，保持与 Web/PWA 的分享链接兼容。
- 建立真正独立的测试沙盒、Windows/Android CI、供应链安全、签名和分阶段发布门禁。
- 延续项目红线：匿名、服务器不持有 E2E 密钥、不记录个人信息/IP、访问次数原子守卫、文件全链路流式。

### 1.2 v0.3 不包含

- Android 后台剪贴板监听、默认输入法、无障碍服务、悬浮窗或规避电池优化。
- 默认开启 Windows 自动上传、开机启动或自动覆盖剪贴板。
- 在一期客户端中直接加入账号、密码、广告、第三方分析 SDK、崩溃内容上报。
- 测试连接生产服务器或复用开发/生产数据卷。
- 未经独立协议设计就使用现有“读取即消费”的 `/api/v1` 轮询实现同步。

设备自动同步、配对和云端历史属于后续 `v0.4-S1`；它们会产生匿名但可关联的频道元数据，必须单独接受隐私决策。

## 2. 当前基线与差距

### 2.1 现有能力可直接复用

| 能力 | 当前接口/实现 | 客户端一期用途 |
|---|---|---|
| 创建文本 | `POST /api/v1/shares` | 显式发送文本 |
| 读取文本 | `GET /api/v1/shares/{code}`/`raw` | 按短码领取；必须禁自动重试 |
| 上传文件 | `POST /api/v1/files` | 使用流式 multipart，不整读内存 |
| 文件元数据/下载 | `GET /api/v1/files/{code}`、`download` | 展示元数据和流式保存 |
| 有效期/次数 | 服务端强制 | 客户端仅展示，不在本地自行判定真值 |
| E2E | WebCrypto `ENC1` + URL fragment `#k=` | 移植到 C#/Kotlin，服务端继续零密钥 |
| 统一错误 | Problem Details 风格 | 两端映射为稳定领域错误 |

### 2.2 上线前 P0 差距

G0 已关闭一项前置风险：测试不再复用开发 Compose 或持久卷；破坏性数据库夹具具备配置目标、沙盒证明和连接后实际数据库身份熔断，数据库与 HTTP 测试目标均限制在本轮内部服务。

仍未关闭的 P0 差距：

1. 生产入口目前仍是 HTTP；原生 Release 必须只允许受信任 HTTPS。
2. C1 工作树已实现 OpenAPI 版本、Problem Details 媒体类型、RFC 3339 UTC、
   `no-store`、消费/重试扩展与加密大小口径，但尚未由 Docker Full Gate 生成并审阅
   OpenAPI 快照，因此仍不能视为已冻结。
3. C1 工作树已为创建/上传实现有限期幂等键、请求摘要和 PostgreSQL 事务锁；读取端点
   按 ADR-0002 冻结为“服务器授权领取即消费”，客户端禁止自动重试并把断线显示为结果
   未知。并发与迁移验证尚待 Full Gate。
4. WebCrypto、C# 与 Kotlin/JCE 合约项目已共同消费非零 key/IV、Unicode/NUL/CRLF、
   二进制边界及共享负向向量；固定容器交叉验证尚未完成。
5. 现有 CI 没有 Windows、Android Emulator、覆盖率硬阈值、安全扫描、SBOM、签名和制品证明。
6. 没有 Windows Publisher/发布渠道、Android applicationId/Play App Signing 与隐私政策决策。

## 3. 技术决策

技术栈采用 [ADR-0001](adr/0001-客户端采用两端原生架构.md)：

| 平台 | 技术栈 | 产物 | 首发范围 |
|---|---|---|---|
| Windows | .NET 10 LTS + C# + WinUI 3/Windows App SDK | MSIX | Microsoft 支持期内的 Windows 11 x64；ARM64 后续加入 |
| Android | Kotlin + Jetpack Compose + Coroutines + Room + WorkManager | AAB；内部测试 APK | `minSdk 29`，当前 `compileSdk/targetSdk 36` |
| 后端 | 现有 Python 3.12 + FastAPI/PostgreSQL | OCI 镜像 | `/api/v1` 兼容；同步另建 `/api/v2` |

共享的是“契约”，不是 UI：`contracts/openapi/`、`contracts/crypto-vectors/`、错误码、威胁模型和场景测试必须成为三端共同真源。

## 5. 分层与接口边界

两端都采用 Ports & Adapters/单向依赖：

```text
UI/平台事件 → Application Use Cases → Domain/Contracts
                              ↓
        ApiPort / CryptoPort / HistoryPort / ClipboardPort
                              ↓
          HTTP / OS Crypto / SQLite / 平台系统适配器
```

硬边界：UI 不得直接调用 HTTP、SQLite、DPAPI/Keystore 或 Win32/Android Framework；业务测试注入 fake port，不触碰真实系统状态。

### 5.1 Windows 模块

- `App`：WinUI 页面、设置、历史、状态和本地化。
- `Application`：发送、领取、下载、暂停监听、历史恢复、重试与取消。
- `Infrastructure`：`HttpClient`、流式 multipart/download、SQLite 密文记录、日志脱敏。
- `Platform`：`AddClipboardFormatListener`、`RegisterHotKey`、`Shell_NotifyIcon`、单实例、通知、DPAPI。
- 自动上传默认关闭；开启后具备 debounce、内容哈希去重、自写回环抑制、暂停按钮、大小/类型限制和明显状态提示。

### 5.2 Android 模块

- `app`：Compose Navigation 与依赖装配。
- `core:*`：领域模型、协议、AES-GCM、Room 密文历史、测试替身。
- `feature:create/receive/history/settings`：按功能隔离 UI 和状态。
- 文本通过前台粘贴或 `ACTION_SEND`；文件通过 `content://`/SAF 流式读写，不申请全盘存储权限。
- WorkManager 只承担用户已发起任务的可靠重试；不得宣称或实现后台实时剪贴板监听。

## 6. 安全与隐私设计

### 6.1 网络与协议

- Release 仅允许 HTTPS，Debug/Test 仅允许显式 loopback/mock；测试守卫拒绝公网写请求。
- 统一超时、取消、指数退避和 `Retry-After`；对当前消费型 GET 禁止自动重试。
- `POST /shares`、`POST /files` 使用 `Idempotency-Key`，服务端存请求摘要和有限期结果；
  消费型读取不复用创建幂等机制，未来若需可恢复领取必须设计新版本短期 claim 协议。
- URL fragment 中的 E2E 密钥不写日志、不进入请求头/query、不进入遥测；分享 URL 展示和复制时提供敏感提示。

### 6.2 E2E 与本地历史

- 保持现有 `ENC1` 兼容，但先冻结字节级格式、Base64URL、IV 长度、AAD 和明文/密文大小口径。
- 每个测试向量固定 key、IV、明文、密文和错误结果；WebCrypto、C#、Kotlin 三端必须逐字节一致。
- Windows 设备密钥由当前用户 DPAPI 保护；Android 由 Android Keystore 保护。大内容不直接写 SecureStorage。
- Room/SQLite 只存密文内容和最少元数据；本地历史默认有限期，可一键清空，不参与系统云备份。
- 日志只记录事件类型、匿名 request-id、状态和耗时；不记录内容、短码完整值、fragment、能力令牌、文件名或路径。

### 6.3 Android 权限最小化

一期不申请：`MANAGE_EXTERNAL_STORAGE`、旧式全盘读写、悬浮窗、无障碍、默认输入法、忽略电池优化。通知权限按功能延迟请求；无通知/后台任务时不预先索取。

## 7. 测试沙盒方案

### 7.1 G0 已交付的保险

- `test_harness/compose.test.yml`：随机唯一项目名、`clipshare_test`、PostgreSQL/文件 `tmpfs`、三张内部网络、无宿主端口、无开发/生产卷。
- 后端破坏性夹具在导入数据库模块前验证 `ENVIRONMENT=test`、固定 `db-test:5432`、`_test` 数据库名和运行时沙盒令牌；连接后再读取 `current_database()` 与 `inet_server_port`。任一项不符都会在建表、迁移、清表或写入前失败。
- 当前 Web/Node HTTP 守卫只接受内部 `http://app-test:8000/`，拒绝 loopback、公网/生产地址、错误端口、凭据、query、fragment 和跨源重定向；未匹配允许路径的请求立即失败。
- `scripts/test-sandbox.ps1` 负责后端/集成测试的 run-id、项目内临时目录、验证、证据和本轮资源清理；客户端合约测试转交 `scripts/test-clients.ps1`。
- G0 已实测 Python/npm 的 home/cache/scratch/report/temp 重定向；脚本已预配置 .NET/NuGet/MSBuild 与 Gradle/Kotlin/Android 的项目内路径，但客户端尚未创建，因此其构建目录和 daemon 残留验证分别留到 W1/A1。
- Docker 测试服务均有 CPU、内存、swap 与 PID 上限；服务使用只读根文件系统、非 root、`cap_drop: ALL`、`no-new-privileges` 和限额 `tmpfs`，基础镜像按 SHA-256 摘要固定。
- Windows/Android 合约测试固定复用 `clipshare-test-dotnet` 与 `clipshare-test-kotlin`：工具链和依赖只准备一次，每轮只替换容器内 `/work/current` 源码并在 `network=none` 下执行，结束后停止且 `restart=no`。不再创建专用 Buildx builder或反复导入、导出缓存。
- 后端/集成资源仍按 run-id 打标签，清理时只删除精确匹配的本轮资源和测试镜像，不允许全局 prune；清理后的标签查询必须为空。
- 清理后还必须比较运行前后的既有容器、网络、卷和镜像清单；任何外部资源状态变化都使测试失败。现有 `clipshare` 资源虽经用户授权可用，G0 仍不连接其持久数据库；其他项目资源只读盘点。

W1/A1 必须继续实现并验收以下平台保险，不能把它们视为 G0 已交付：

- Windows/Android Test build 只能访问显式 loopback mock；Android 模拟器仅可额外访问映射本机沙盒的 `10.0.2.2`。已知生产地址和其他公网地址无条件拒绝，未匹配 mock 请求立即失败。
- 普通测试使用 fake clipboard/tray/hotkey/notification/filesystem。Windows 真适配器仅在禁用宿主剪贴板共享的 Windows Sandbox/临时 VM；Android UI/系统测试使用可丢弃 Managed Device。
- Windows `.wsb` 必须 `Networking=Disable`、`ClipboardRedirection=Disable` 且源码只读映射，mock/backend 同沙盒运行；Android E2E 在可丢弃模拟器/临时 CI VM 中运行，并由测试构建 URL 守卫拒绝非 mock 目标。

G0 的 Guard 与 Full 验收证据见 [v0.3-G0 测试沙盒验收记录](依据/v0.3-G0-测试沙盒验收记录.md)。G0 完成后仍禁止绕过 `scripts/test-sandbox.ps1` 直接运行会访问数据库或 HTTP 的测试。

| 层级 | Windows | Android | 后端/契约 |
|---|---|---|---|
| 单元 | xUnit：use case、去重、URL 守卫、错误映射 | JUnit：ViewModel/use case、WorkManager 策略 | pytest：领域与服务 |

### 7.3 覆盖率和质量阈值

- 核心/共享领域：行 ≥90%，分支 ≥85%；
- 平台适配层：行 ≥80%；
- 变更行：≥90%；
- 加密、URL 守卫、幂等、同步去重/回环抑制：关键场景 100%；
- 编译警告视为错误；Python ruff/mypy strict、.NET analyzers、Android lint/detekt 零错误；
- Critical/High 依赖或 SAST 漏洞为 0。

## 8. CI/CD 与上线门禁

### 8.1 PR 必需检查

1. `governance`：Agent 范围、文档/ADR、生成文件和锁文件一致性；
2. `backend-lint-test`：专用沙盒内 ruff、mypy、pytest、迁移和 OpenAPI diff；
3. `web-e2e`：本地沙盒 API；
4. `windows-build-test`：Windows runner，编译、单元、契约、打包验证；
5. `android-lint-unit`：Gradle lint/detekt/unit；
6. `android-emulator`：Managed Device UI/系统测试；
7. `security`：CodeQL/SAST、依赖审查、密钥扫描、SBOM、许可证；
8. `package-unsigned`：生成不可发布测试制品、SHA-256 和来源证明。

任何发布 job 必须 `needs` 全部必需检查；PR 产物不得使用生产签名。

### 8.2 Release Gate

只有同时满足以下条件才可进入签名环境：

- `main` 受保护，PR 和全部必需检查通过；
- 威胁模型、隐私说明、Data Safety/商店资料与变更日志审查完成；
- OpenAPI/密码学兼容测试、安装升级、卸载清理、回滚演练通过；
- SBOM、SHA-256、漏洞报告、测试报告和构建来源证明归档；
- Windows 通过 MSIX 签名/商店认证，Android 通过 Play App Signing/AAB 预发布检查；
- 签名密钥由 GitHub Environment/人工保管，Agent 与普通 PR job 无权读取；
- 生产域名 HTTPS、staging 和监控/回滚准备就绪。

发布采用内部测试 → 5% → 25% → 100% 分批推进；安全错误、崩溃或协议失败超过阈值立即暂停，回滚上一已签名制品。正式版本证据建议保存至少 3 年。

## 9. 多 Agent 执行编排

遵循根目录 `AGENTS.md`，每个模块只有一个实现 Agent。建议角色池：

- Windows 实现 Agent；
- Android 实现 Agent；
- 后端/契约实现 Agent；
- 安全审查 Agent（只读）；
- QA/发布审查 Agent（只读）；
- 文档 Agent。

角色池不等于并发写入。主控每次只向一个实现 Agent 发放明确文件写租约；安全与 QA 可并行只读。所有 Agent 都是当前项目内临时 Agent，完成即关闭，不修改全局配置。

| `v0.4-S1` 匿名设备同步 | 能力频道、配对、密文事件、游标、撤销 | 必需：独立隐私评审、威胁模型、幂等/重放/撤销/并发/负载测试 | 单独决策 |

每模块使用 Conventional Commits 中文提交，例如 `chore(v0.3-G0): 建立客户端测试沙盒`；实现、审查、修复、适用验证、文档缺一不可。任何 N/A 项都必须在 PR 中给出理由并由主控批准。

## 11. v0.4 同步协议边界

现有 API 不具备同步语义。后续协议建议：

- 匿名高熵频道 ID；读、写、管理能力令牌分离，服务器只存令牌哈希；
- 配对 QR 在设备间直接传递能力与 E2E 频道密钥，管理令牌不分享；
- 事件带 UUID、单调游标、`Idempotency-Key`、请求摘要和 AEAD AAD；服务器只存有限期/有限额密文；
- 首版用短长轮询，验证负载后再考虑 WebSocket；Android 后台限制不会因 WebSocket 消失；
- 无账号恢复：所有设备和密钥均丢失时，服务器不能恢复明文，这是 E2E 的必然后果；
- 稳定频道会形成匿名但可关联元数据，必须在开发前由用户确认隐私取舍。

## 12. 立项结论

项目已完成 `v0.3-G0`，但当前上线结论仍明确为 **NO-GO**。下一步只能执行 `v0.3-C1`：冻结 OpenAPI/错误语义/UTC/幂等约束并建立 Web、C#、Kotlin 共用的 `ENC1` 密码学向量；在 C1 验收前不得开始 Windows/Android 业务 UI。

G0 之后按 `C1 → W1 → A1 → C2 → W2/A2 → R1` 串行推进，每一阶段都由实现、只读安全审查、只读 QA 审查、修复、沙盒验证和文档形成闭环。

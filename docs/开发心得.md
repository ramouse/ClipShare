# 开发心得 — ClipShare 云剪切板分享系统

> 作者：NAME（占位，交付前替换真实姓名）
> 项目：比特工场 2026 暑期技能提升项目 · 目标等级：特等奖
> 本文基于开发全过程（M1 工程脚手架 → M6 生产部署基础设施）的真实记录整理，素材来源为各模块学习手册的踩坑记录与代码注释。所有"坑"都是开发中实际发生并解决的，不是事后编造。

## 一、架构取舍

### 1. "领域层是纯函数"是怎么来的

项目要求业务核心逻辑覆盖率 ≥90%，还要在并发下不破坏"超限禁止访问"红线。我们最初把有效期、次数判定逻辑放在服务层里，测试要连数据库。后来把决策改成了：**领域层（`app/domain/`）只放无框架依赖的纯策略函数**（`expiry.py`、`access.py`、`shortcode.py`），时间、次数等全部显式作为参数传入，不 mock 任何东西就能单测；ORM 模型放数据层（`db/models.py`），路由层禁止直接访问数据库，分层依赖单向：`api → services → domain`。

这个取舍的直接收益是：M2 的单元测试几乎零成本，而"有效期 4 档"、"次数 3 档"这类最容易被改坏的规则被钉死在纯函数测试里。代价是分层文件变多，但每个文件都短、职责单一。

### 2. "页面 shell 架构"：让访问计数只经 API 一次

查看页最容易被做成"服务端渲染内容"，但那样打开页面就消耗一次访问次数——`max_views=1` 的分享，自己点开看一次就没了，体验是坏的。我们的方案是：**HTML 页面只是 shell（不读数据库、不判存在性），内容由前端 JS 只调一次读取 API 获取**；页面浏览不计次，真正读到内容才计次。错误页也由前端按 API 错误体的 `type` 字段渲染。配套三个测试把这个契约钉死：shell 不读库（内容绝不出现在页面 HTML 里）、计数只经 API 一次、任意短码都返回 200 的 shell。

### 3. 为什么二维码并入 shares 路由、不单建文件

开发方案最初预列了一个独立的 `qr.py` 路由文件。审查阶段我们确认"同资源同文件"原则——二维码是分享资源的子端点，并入 `shares.py` 的 `/{code}/qr`。顺带明确了两个容易被忽略的语义：**二维码不消耗访问次数**（扫码后打开分享页才计次）、**不判过期**（过期与否由网页端读取时判定，扫过期链接会看到友好错误页而非 404）。

### 4. 技术选型（简要）

- **FastAPI**：类型驱动的请求/响应模型，自动生成 OpenAPI 文档，`/docs` 免费获得；
- **PostgreSQL + SQLAlchemy 2.0 + Alembic**：项目书推荐生产用 PG；守卫式原子自增（§三）需要真实的数据库层并发语义；
- **前端零构建**（Bootstrap 5 + 原生 JS + marked + highlight.js + DOMPurify，全部 vendored）：部署简单、手机端够用，且把创新点（加密/CLI）的实现成本降到最低；
- **Docker Compose 全容器化**：本机 Python 3.8 与项目要求 3.12 不一致，"一切验证进容器"用环境统一消灭了"我本机能跑"这类争议（见 §五坑 4）。

## 二、隐私红线落地

项目书要求"不记录用户个人信息与 IP"。这条红线在代码里是逐层落地的：

### 1. 三个容易漏的"默认行为"

我们自己写的代码确实没记 IP：structlog 只记短码与状态、限流计数器选内存型存储（瞬时计数、重启清零、天然不落盘）。但审查阶段发现 **uvicorn 的 access log 是框架默认行为**——每个请求一行 `INFO: 127.0.0.1:54321 - "POST ..." 201`，IP 和端口被全量、静默地写进容器日志。红线就这样被"默认行为"击穿，而我们自己的日志代码一行都没写。修复：应用启动加 `--no-access-log`；生产 nginx 同样 `access_log off`。

教训：**隐私红线的排查对象包括"框架和中间件默认会记录什么"**，而不只是自己写的日志调用。

### 2. 密钥只放 URL fragment

E2E 加密的密钥（32 字节随机数）拼在分享链接 `#k=…` 之后。fragment 的语义是"客户端本地片段"，**不随 HTTP 请求发送**——这是协议层面的保证，不是靠自觉。配合 `Referrer-Policy: no-referrer`（短码不外泄到第三方站点），构成双层防护。验证手段是三层证据：SQL 直查数据库断言"落库即密文"、E2E 断言"整个响应体不出现明文"、协议层文档说明 fragment 不发送。

### 3. IP 用于限流但不落盘

限流按 IP 判定（slowapi 内存计数），IP 只进内存计数器、不进日志、不进数据库。生产反代必须用 `$remote_addr` 覆盖客户端可伪造的 `X-Forwarded-For`，否则限流可被伪造 IP 绕过——这条留痕在代码注释与部署手册安全清单里。

## 三、并发正确性

### 1. "先判定、后自增"的竞态，被审查挡下

M2 初版打算由服务层"先判定未耗尽、再自增计数"。审查 Agent 指出：两个并发请求可能同时通过判定、随后双双自增，把计数顶过上限——**红线在并发下形同虚设**。修复是守卫式原子自增 `increment_view_count_guarded`：把"未耗尽"判定下推成 UPDATE 的 WHERE 谓词（`max_views IS NULL OR view_count < max_views`），判定与自增在同一行锁内原子完成。配套 3 个集成测试，用 10 线程 × 10 次并发实证计数精确、且耗尽后计数不再增长。

教训：**凡红线都必须假设并发**。"先查后改"在任何数据库下都有窗口，条件更新要么用带谓词的 UPDATE，要么 SELECT ... FOR UPDATE。

### 2. "自增没坏，是断言读旧了"

并发测试一度"失败"：断言 `view_count == 100` 读到 0。排查后确认不是丢更新，而是 **SQLAlchemy 身份映射缓存**——fixture 会话里 `expire_on_commit=False`，commit 后实例属性停留在加载时快照，同一 session 再查同一主键返回的是内存里的旧对象。修复：断言前开独立会话读回数据库真值。这个坑让我们学到：**凡是断言"数据库当前状态"必须用新会话**；并发排查要先分清"写丢了"还是"读旧了"。

### 3. 限流预算是全套件共享的

测试套件跑在一个进程里，slowapi 的 `memory://` 计数器共享——**"30/min"不是每个测试文件 30 次，是整个 pytest 进程 30 次**。注意限流检查在路由函数内执行，参数校验（422）发生在其之前，**422 不消耗额度**，预算主要来自 201 创建请求（我们曾误以为是"422 也占额度"，实测 30 次 422 后合法请求仍 201 才纠正）。我们把创建类用例数显式预算（套件约 18 次创建），把 429 用例放在文件最后循环触发，并在代码注释里写明预算规则，防止后人加用例时悄悄超限。

## 四、XSS 防御

"禁止直接把用户输入 innerHTML"是项目书强制项，我们的落实是三层，不是一行代码：

1. **非富文本全走 `textContent`**（纯文本、JSON、元信息、错误信息）——根本不解析 HTML，没有转义表可漏；
2. **富文本（marked / highlight.js）输出必须先过 DOMPurify 白名单才 `innerHTML`**——不假设任何第三方库的输出绝对安全；外链统一 `target="_blank"` + `rel="noopener noreferrer"`（分享链接本身就是访问凭据，不能让它带 referrer 外泄）；
3. **CSP 收窄执行面**：`script-src 'self'`（禁内联脚本，页面 JS 全部走文件）、`style-src 'self'`（不加 unsafe-inline）、`frame-ancestors 'none'` + `X-Frame-Options: DENY` 防点击劫持。

jsdom 冒烟脚本用真实页面 + 注入 XSS 载荷（`<img onerror>`、`<script>`）实证：消毒后 DOM 里一个注入节点都不剩、alert 从未触发。**安全特性必须自带可验证的断言**——"设计上应该不会"不算数。

## 五、AI 协作工作流

本项目采用"主控 + 实现 + 审查 + 文档"多 Agent 流水线：实现 Agent 写代码跑验证门，审查 Agent 只读对抗性审查（专门盯红线和契约），文档 Agent 并行写学习手册，主控统一提交。几点真实体会：

1. **审查真的能抓到东西**：超卖竞态（§三 1）、access log 隐私击穿（§二 1）、`parseIsoUtc` 正则自身 bug（"避免重复补 Z"的正则漏掉了独立 `Z` 结尾）都是审查环节发现的。"审查只盯自己写的代码"是不够的，还要盯框架默认行为与补漏代码自身的漏洞。
2. **接口契约先行 + 回写决策**：模块间接口在派发任务时以契约为准，实现中改接口必须回写开发方案 §7 决策记录——`qr` 归属、领域层无 models.py、守卫自增都是这么沉淀的。
3. **学习手册与代码同步交付**：每个模块一章手册（目标/技术要点/代码导读/验证命令/踩坑记录），"文档与代码不一致以代码为准"是铁律。这篇心得的大部分素材就直接来自手册 §5 踩坑记录。
4. **"一切验证进容器"消灭环境争议**：本机 Python 3.8 vs 项目要求 3.12，升级本机不是答案，把验证命令固定为 `docker compose run --rm app <cmd>` 才是——"开发环境 = 生产环境"从口号变成事实。
5. **给 AI 的坑也是给后来者的坑**：几乎所有踩坑都在代码里留了注释（"为什么这么做""为什么不那样做"），`# noqa` 必须带意图说明，工具豁免必须带注释——这些是让 AI 协作项目可持续的隐性文档。

## 七、写在最后

这个项目让我完整走了一遍"需求红线 → 分层设计 → 审查加固 → 验证门 → 文档沉淀"的工程闭环。最大的收获不是某个具体技术，而是三条可迁移的认知：**红线必须假设并发与默认行为**（不看"应该"看"实际"）；**可验证性是一等需求**（每条安全声明都要有断言或命令证明）；**让后来者（包括 AI）少踩坑的最好方式是把为什么写进代码注释与文档**。
